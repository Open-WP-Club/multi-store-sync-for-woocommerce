## RENEW — outdated approach vs current WP/WC/PHP standard

- [~] `includes/api-client.php:254-338` vs `includes/webhook-receiver.php:45-77` — two independent rate-limiter implementations reinvent the same `wp_cache_add`+`wp_cache_incr`/transient-fallback technique. Extract one shared helper. **Reviewed, not touched**: these serve different purposes with different precision needs — `api-client.php` self-throttles the plugin's own *outgoing* API calls and needs to compute an exact wait-time (true sliding window merging in-memory + transient timestamps in its fallback path), while `webhook-receiver.php` rejects *incoming* requests over a threshold with a simple boolean/count (its fallback is a much simpler non-atomic counter). Only the object-cache fast path's 2-line `wp_cache_add` + `wp_cache_incr` idiom is genuinely identical; extracting a shared helper for just that would save 2 lines twice while the two functions' surrounding logic (and fallback behavior) stay completely different — marginal enough that it isn't worth a new shared primitive.
- [~] `includes/circuit-breaker.php:146-156` — independently reimplements transient-based state storage rather than extending `Cache_Manager`. Third parallel transient-cache implementation for the same pattern. **Reviewed, not touched**: unlike the sync-engine.php term cache (genuinely stale-data-risk caching of remote API responses — Cache_Manager's stated domain), circuit-breaker state is *protective*, not a performance cache — it deliberately should NOT be swept by a generic "clear all caches" admin action (that would resume hammering a store that's circuit-broken for a good reason; there's a separate explicit `reset()` for that). It also needs a MySQL advisory lock around its read-modify-write that `Cache_Manager` doesn't provide and has no reason to. Routing it through `Cache_Manager` would mean either adding a valueless generic pass-through method, or making protective state sweepable by a blanket cache-clear action — the latter would be a behavior regression, not a cleanup.
- [~] `includes/category-mapper.php`, `attribute-remapper.php`, `shipping-class-sync.php`, `downloadable-files-sync.php` — each kept settings under its own `get_option()` key instead of the central `WC_Multi_Store_Settings` store. _(partial — the `enabled`/`auto_sync_on_change`/`transfer_mode` flags for all 4 classes now live in the central store as `{prefix}_enabled` etc. (e.g. `shipping_class_sync_enabled`), consistent with `stock_sync_enabled`/`image_proxy_enabled` already there. `WC_Multi_Store_Toggleable_Feature::migrate_settings_to_central_store()` (`includes/toggleable-feature-trait.php`) one-time-migrates each class's legacy option into the central store and deletes the legacy option, wired into `maybe_upgrade_database()` (bumped to db version 1.9) so existing installs carry their current toggle state forward automatically on next admin/cron/AJAX request after upgrading — no manual action needed, and fresh installs just no-op through it._
  **TODO(v5.0): remove the migration.** `migrate_settings_to_central_store()`, its call site in `maybe_upgrade_database()`, and the now-legacy `SETTINGS_KEY` constants in all 4 classes exist only to carry forward pre-migration installs. Once enough time has passed that every real install has upgraded through db version 1.9 at least once (the legacy option gets deleted the first time it runs), this whole migration path is dead weight — delete it in the next major version rather than carrying it indefinitely.
  **Not migrated — left as a separate, harder problem**: `category-mapper.php`'s and `attribute-remapper.php`'s actual mapping-data options (`wc_mss_category_mappings`, `wc_mss_tag_mappings`, `wc_mss_attribute_name_mappings`, `wc_mss_attribute_value_mappings`) are keyed by `md5($store_url)`, while the central store's per-store precedent (`pricing_rules`/`stock_allocation_rules` as sub-keys of each store's config in `wc_multi_store_sync_stores`) is keyed by literal store URL. Moving these would mean re-deriving `md5(url) → url` for every currently-known store to re-key the data, with no clean answer for orphaned entries belonging to since-deleted stores.

  **Follow-up, resolved**: the AJAX endpoints that write/read this mapping data (`ajax_save_mappings()`/`ajax_get_mappings()` on both classes, `wp_ajax_wc_mss_save_category_mappings`/`wp_ajax_wc_mss_get_category_mappings`/`wp_ajax_wc_mss_save_attribute_mappings`/`wp_ajax_wc_mss_get_attribute_mappings`, all registered in `class-admin-ajax.php`) are live, nonce- and capability-checked, and fully functional — but genuinely have no caller anywhere in `admin/js/admin-scripts.js` or any `admin/views/*.php`. Root cause: `settings.php`'s "Category Mapping" toggle description said _"Configure mappings in each store's settings"_, pointing at a per-store mapping screen that was never built — the toggle enables a feature with no way to actually enter mapping data. Fixed the misleading copy on both the Category Mapping and Attribute Remapping toggles (plugin owner's call: fix the description, leave the endpoints in place for a future UI rather than removing them or building that UI now) — both now say plainly that there's no admin screen yet to enter mappings, so enabling the toggle alone does nothing.
- [~] `md5($store_url)` independently re-derived as a cache/meta-key fingerprint in `product-extractor.php`, `category-mapper.php`, `attribute-remapper.php`, `product-edit.php`, `remote-product-manager.php`. One shared `StoreKey` helper would remove the repetition. **Reviewed, not touched**: actually appears in ~15 files, not the 5 named. A wrapper class/method around a single stdlib call (`md5($x)`, 11 characters) would replace it with a longer static-method call everywhere — less lazy, not more, and doesn't reduce real complexity. Only worth revisiting if the hashing scheme itself ever needs to change (e.g. to sha256), which is speculative, not a current need.
- [~] `admin/views/dashboard.php:147-303` + `admin/views/weekly-verification.php:431-591` — ~150-line inline `<script>` for verification start/poll/cancel. **Reviewed, not touched**: not near-identical on closer read — deliberately different UX per context. Idle-poll timeout is 5×3s (~15s) in dashboard.php vs 40×3s (~2min) in weekly-verification.php; on `completed` dashboard.php resets the UI while weekly-verification.php calls `window.location.reload()`; on idle-exceeded dashboard.php resets + shows an error while weekly-verification.php leaves the progress bar visible (orange, cancel hidden) without resetting; weekly-verification.php has an extra `pending` status branch dashboard.php doesn't; `startVerification()` has a `.catch()` in dashboard.php but not in weekly-verification.php; button/status label text differs throughout. A shared helper would need a config object for 10+ divergent behaviors — the same "config for values that never change" trap already flagged elsewhere in this doc — and there's no JS test coverage to catch a regression in either flow. Left as two intentionally-different implementations.

## MODERNIZE — PHP 8.4 is already the minimum version; use its features consistently

- [~] `includes/queue-manager.php:18-21` — `PRIORITY_CRITICAL/HIGH/NORMAL/LOW` bare int constants (1/2/3/10). **Not converted to backed enum**: the `priority` column is an ordinal 1-10 scale, not a closed set — `queue-table.php::add()` defaults `$priority = 5` and branches on `$priority < 5` (line 164) to decide whether to bump an existing queue item's priority; `5` isn't one of the four named constants, and `get_next_batch()` sorts with plain `ORDER BY priority ASC`. Every call site (`queue-manager.php`, `queue-table.php`) types `$priority` as bare `int`, and reflection-based tests (`QueueManagerTest.php:189`) assert `getDefaultValue()` against the raw int. A 4-case enum can't represent the full domain this column actually stores/compares — the named constants are presets within a wider ordinal scale, not the type itself.
