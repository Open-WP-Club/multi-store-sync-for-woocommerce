# WooCommerce Multi-Store Sync - Claude Context File

## Project Overview

**Plugin Name:** WooCommerce Multi-Store Sync
**Version:** 3.8.0
**Type:** WordPress/WooCommerce Plugin
**Requires:** PHP 8.4+, WordPress 5.8+, WooCommerce 6.0+ (tested to 9.5)
**Architecture:** Object-oriented, singleton pattern, Composer classmap autoloading (`composer.json` → `"classmap": ["includes/"]`)
**Purpose:** Synchronize products, inventory, coupons, shipping classes, and orders from one main WooCommerce store to multiple remote stores

## Core Architecture

### Key Design Patterns

1. **Singleton Pattern**: Main plugin class and most core classes
2. **Dependency Injection**: API client injected into sync engine
3. **Hook-based Architecture**: WordPress actions/filters throughout
4. **Caching Strategy**: Reduce API calls with intelligent caching
5. **Queue System**: Background processing for large operations
6. **Autoloading**: Composer's classmap autoloader (`vendor/composer/autoload_classmap.php`, generated from `composer.json`'s `"classmap": ["includes/"]`) maps every `WC_Multi_Store_*` class to its file — no separate plugin autoloader. Admin-only classes (`product-edit.php`, `remote-order-list-table.php`, `remote-order-admin.php`) are only *instantiated* when `is_admin()` (in `init_admin()`), which is what gates their loading
7. **Resilience**: `circuit-breaker.php` opens per-store after repeated consecutive failures; `dead-letter-queue.php` catches permanently-failed items after retries are exhausted

## Core Classes

### 1. WC_Multi_Store_Sync (Main Class)
**File:** `wc-multi-store-sync.php`
**Purpose:** Plugin initialization and lifecycle management
**Key Methods:**
- `instance()` - Singleton accessor
- `activate()` - Plugin activation hook

### 2. WC_Multi_Store_API_Client
**File:** `includes/api-client.php`
**Purpose:** WooCommerce REST API communication wrapper
**Key Methods:**
- `get_product($store, $product_id)` - Fetch remote product
- `create_product($store, $data)` - Create new product
- `update_product($store, $product_id, $data)` - Update product
- `batch_update($store, $data)` - Batch operations
- `test_connection($store)` - Verify API credentials

**API Authentication:**
- Supports query string and header authentication
- Uses WooCommerce REST API v3

### 3. WC_Multi_Store_Sync_Engine
**File:** `includes/sync-engine.php`
**Purpose:** Core product synchronization logic

### 28. Autoloading (no longer a plugin class)
**Removed:** `includes/class-autoloader.php` / `WC_Multi_Store_Autoloader` (deleted — was a redundant hand-maintained class map duplicating what Composer already generates)
**Purpose now:** `wc-multi-store-sync.php`'s `includes()` method only requires `vendor/autoload.php`. Composer's classmap autoloader (`vendor/composer/autoload_classmap.php`, generated from `composer.json`'s `"classmap": ["includes/"]`) already maps every `WC_Multi_Store_*` class to its file, including the naming exceptions (`WC_Multi_Store_Admin_Ajax` → `class-admin-ajax.php`, `WC_Multi_Store_Settings_Integration` → `wc-settings-integration.php`)
**To find a class's file:** `grep "WC_Multi_Store_ClassName" vendor/composer/autoload_classmap.php`, or just search `includes/` directly
**Admin-only classes** (`product-edit.php`, `remote-order-list-table.php`, `remote-order-admin.php`) load lazily the moment they're `new`'d inside `init_admin()`, which is itself gated on `is_admin()` — no eager require needed

## Hooks & Filters

**This section reflects a full `wc_mss_*` audit of the codebase as of 3.7.2.** The plugin's actual custom hook surface is much smaller than earlier drafts of this file assumed — several previously-documented hooks (`wc_mss_before_sync`, `wc_mss_after_sync`, `wc_mss_before_order_sync`, `wc_mss_after_order_sync`, `wc_mss_should_sync_product`, `wc_mss_batch_size`, `wc_mss_sync_types`, `wc_mss_cache_expiration`) do not exist anywhere in the code and have been removed from this doc. If you need equivalent extension points, use the `Development Guidelines` patterns below as a starting point for adding them, or hook the underlying WordPress/WooCommerce actions directly (see "WordPress Hooks (Plugin Uses)").

### Actions (Plugin Provides)
```php
// Fired after every outbound API call — logs usage stats (api-usage-tracker.php, api-client.php)
do_action('wc_mss_api_request', $store, $endpoint, $method, $response_data);

// Product sync failure — triggers email notification (email-notifications.php)
// $error_message is always a plain string, not a WP_Error
do_action('wc_mss_sync_failed', $product_id, $store_url, $error_message);

// API-level error — triggers email notification (email-notifications.php)
do_action('wc_mss_api_error', $store_url, $error_message);

// Stock below threshold — triggers email notification (email-notifications.php)
do_action('wc_mss_low_stock_detected', $product_id, $store_url, $stock_quantity);

// Item moved to Dead Letter Queue — currently NO consumers, an unused extension point
do_action('wc_mss_dead_letter_added', $queue_item);
```

Custom (non-WooCommerce/WordPress-core) actions the plugin also *consumes*, mostly via Action Scheduler: `wc_mss_archive_history` (log rotation), `wc_mss_async_verification_batch` (weekly verifier batch processing), `wc_mss_send_daily_summary` (daily email summary).

### Filters (Plugin Provides)
```php
// Custom pricing-rule extension point (pricing-rules.php)
apply_filters('wc_mss_custom_pricing_rule', $product_data, $pricing_rules, $product);

// Whitelist trusted proxy IPs for client-IP resolution behind CDNs (webhook-receiver.php)
apply_filters('wc_mss_trusted_proxies', $trusted_ips);

// Exclude additional postmeta keys from the custom-field mapping UI (custom-field-mapper.php)
apply_filters('wc_mss_excluded_meta_keys', $excluded_keys);

// Extend the custom-field mapping list (custom-field-mapper.php)
apply_filters('wc_mss_available_custom_fields', $available_fields);
```

### Adding Custom Sync Logic
```php
// Example: Skip syncing products in specific category
add_filter('wc_mss_should_sync_product', function($should_sync, $product_id, $store_id) {
    $product = wc_get_product($product_id);
    if ($product && $product->has_category('do-not-sync')) {
        return false;
    }
    return $should_sync;
}, 10, 3);
```

## Performance Considerations

### Optimization Strategies
1. **Caching:** Remote products cached for 1 hour
2. **Batch Processing:** Configurable batch sizes (5-20 products)
3. **Peak Hours:** Smaller batches during business hours (6am-11pm)
4. **Queue System:** Prevents duplicate processing
5. **Memory Management:** Explicit cleanup in loops
6. **Database Indexes:** On sync_history table

### Performance Monitoring
- Track duration per sync
- Count API calls
- Monitor memory usage
- Log slow operations (>30s)

### Batch Size Recommendations
- **Peak hours (6am-11pm):** 5 products
- **Off-peak (12am-6am):** 20 products
- **Large catalogs (1000+):** Use queue system
- **Server memory < 256MB:** Reduce batch size

## Security

### Security Measures Implemented
1. ✅ Nonce verification on all forms
2. ✅ Capability checks (`manage_woocommerce`)
3. ✅ Input sanitization (`sanitize_text_field`, etc.)
4. ✅ Output escaping (`esc_html`, `esc_url`, etc.)
5. ✅ Prepared SQL statements (no direct queries)
6. ✅ API credentials stored securely; consumer key/secret/App Password fields in `admin/views/stores.php` render as `type="password"` with `autocomplete="off"` and a Show/Hide toggle rather than plain text
7. ✅ HTTPS required for remote stores
8. ✅ Logs directory protected with .htaccess
9. ✅ `ORDER BY` clauses whitelisted against a fixed column list before use (`deletion-audit.php`, `sync-history.php`, `weekly-sync-verifier.php`) — prevents SQL errors/schema exposure from unvalidated sort parameters
10. ✅ CSV exports guard against formula injection by passing explicit delimiter/quote/escape args to `fputcsv()` (`webhook-logger.php`, `api-usage-tracker.php`)
11. ✅ SSRF guard blocks link-local/private IPs on outbound Application Password test requests (`store-health-check.php`)
12. ✅ Default API `auth_method` is `basic_auth` (not `query_string`, which can leak credentials in server/proxy logs) across `remote-order-sync.php`, `stock-verifier.php`, `store-health-check.php`, `sync-previewer.php`
13. ✅ Regression coverage for the above lives in `tests/php/Unit/SecurityRegressionTest.php` (capability checks, SSRF blocking, ORDER BY whitelists, CSV guards, auth_method fallbacks) — this replaced a standalone `SECURITY_REPORT.md` that has been removed from the repo now that its findings are codified as tests

### Security Best Practices
- Use unique API keys per store
- Read/Write permissions only (not Admin)
- Rotate credentials periodically
- Monitor sync logs for anomalies
- Keep WordPress/WooCommerce updated
- Use strong passwords for API keys

### Rate Limiting
- No built-in rate limiting on outbound product/order API calls to remote stores — remote store may have its own limits; use the queue system for large operations
- Email notifications (failure/API-error/low-stock) are self-rate-limited to 1 per 12 hours per type via transients (`email-notifications.php::claim_daily_slot()`)
- `circuit-breaker.php` provides a related (but distinct) protection: it halts requests to a specific store after 10 consecutive failures for 1800s, rather than limiting request rate

### API Usage Tracking
`api-usage-tracker.php` logs every outbound API call (`wc_mss_api_request` action) to the `wc_mss_api_usage` table and exposes per-store/per-endpoint stats, daily trends, and cost estimates in **Multi-Store Sync > API Usage**.

## Important Notes

1. **This is a STANDALONE plugin** - Does not require any other plugins except WooCommerce
2. **Product/inventory sync is one-way** - Main store → Remote stores (not bidirectional). **Order data flows both ways**, though: `order-sync.php` pushes inventory changes out on local order completion, while `remote-order-sync.php` + `webhook-receiver.php` pull/receive order data *from* remote stores back into a local read-only cache (Remote Orders admin page) — this is for visibility/reporting, not product sync
3. **Install only on main store** - Remote stores only need WooCommerce
4. **Queue system is crucial** - Don't bypass it for large operations
5. **Cache is important** - Reduces API calls by ~50%
6. **Peak hours matter** - Batch size affects performance
7. **Error handling is robust** - Syncs retry with exponential backoff; a store that keeps failing trips the circuit breaker (`circuit-breaker.php`) rather than retrying indefinitely; items that exhaust retries land in the Dead Letter Queue (`dead-letter-queue.php`) for manual review
8. **Class loading is Composer-classmap-driven** - New classes just need to live under `includes/` with a `class WC_Multi_Store_*` declaration; run `composer dump-autoload` to refresh `vendor/composer/autoload_classmap.php` after adding a file (no manual map to update — the old `class-autoloader.php` was removed as redundant)
9. **All main admin UI is a WooCommerce Settings tab, not a top-level menu** - See `wc-settings-integration.php`; the one exception is the Remote Orders page
